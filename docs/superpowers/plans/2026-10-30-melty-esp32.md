# Melty ESP32 Firmware Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build ESP32 firmware that spins, translates, and fails safe on a two-motor brushed melty, ready for the owner's bench and arena tests.

**Architecture:** All decision logic lives in a hardware-free library, `lib/melty`, tested on the host in WSL. `src/` holds thin ESP32 drivers and one `loop()` that wires them together. Safety state always decides motor output, nothing else can command motors while disarmed.

**Tech Stack:** C++17, PlatformIO, Arduino framework for ESP32, Unity tests on host g++ 14.2 in WSL (default Kali distro).

**Spec:** `docs/superpowers/specs/2026-10-30-melty-esp32-design.md`

## Global Constraints

- iBUS: GPIO16 RX, 115200 8N1. Motor A GPIO25, motor B GPIO26, SDA GPIO21, SCL GPIO22, LED GPIO27.
- Neutral 1500 us. Commanded power maps to 1500 to 2000 us and never crosses neutral. A reversed motor mirrors the same range around 1500, giving 1500 down to 1000 us.
- Used channels: CH1 X, CH2 Y, CH3 spin, CH4 heading trim, CH5 arm.
- iBUS timeout 100 ms. Sensor failure while armed at 500 ms stops translation and LED, keeps spin.
- Jam trigger: above stall cap and below minimum RPM for 1000 ms.
- MPU-6050 at +/-16g, I2C 400 kHz. No WiFi or Bluetooth code.
- No blocking I2C or UART work in the control loop. USB console accepts commands only while disarmed, and never prints while armed.
- Comments are sparse. No em dashes in docs. Conventional commits. No `Co-Authored-By` or generated-by lines.

## Review Focus

- Line noise or a mid-stream connection leaves the parser out of sync: it must resync on the next good frame and never pass a bad-checksum frame. Test in Task 2.
- Frames stop, then resume with SwA armed and sticks anywhere: the robot must stay disarmed. Test in Task 3.
- A hit makes the sensor read clipped, negative, or NaN values: RPM and heading must never become NaN or jump. Test in Task 4.
- Sticks sit exactly centered: no translation and no `atan2(0, 0)` direction. Test in Task 5.
- A USB `set` carries garbage, NaN, or an out-of-range number, or NVS holds corrupt settings: reject it and keep safe values. Test in Task 6.

### Task 2: iBUS parser

**Files:**
- Create: `lib/melty/ibus.h`, `lib/melty/ibus.cpp`
- Test: `test/test_ibus/test_ibus.cpp`

**Interfaces:**
- Produces:
```cpp
struct IbusFrame { uint16_t ch[14]; bool failsafeFlag; };
class IbusParser { public: bool push(uint8_t byte, IbusFrame& out); };
```

Frame is 32 bytes: `0x20 0x40`, 14 little-endian channels, then a little-endian checksum equal to `0xFFFF` minus the sum of the first 30 bytes. `ch[i]` is the low 12 bits. `failsafeFlag` is true if bit `0x2000` is set on any of CH1 to CH5. Only channels 1 to 5 count, as higher channels may use the upper bits for other data.

### Task 3: Arming and failsafe state

**Files:**
- Create: `lib/melty/safety.h`, `lib/melty/safety.cpp`
- Test: `test/test_safety/test_safety.cpp`

**Interfaces:**
- Consumes: `IbusFrame`.
- Produces:
```cpp
constexpr uint16_t kChMin = 900, kChMax = 2100, kArmHigh = 1700, kThrottleLow = 1050, kFullLeft = 1050;
constexpr uint32_t kIbusTimeoutMs = 100;
class Safety {
public:
  void setSensorStartupOk(bool ok);
  void onFrame(const IbusFrame& f, uint32_t nowMs);
  void update(uint32_t nowMs);   // applies the frame timeout
  bool armed() const;
  bool signalOk() const;
};
```

CH5 counts as armed only above `kArmHigh`, anything else is disarmed. Use unsigned subtraction for time. Any failure clears `armed` and requires a fresh disarmed-to-armed edge. Arming checks on that edge only: frames valid, `ch[2] <= kThrottleLow`, `ch[0] <= kFullLeft`, sensor startup ok. If the edge fails its checks, the robot stays locked until CH5 goes back to disarmed. A first frame showing CH5 armed is not an edge.

### Task 4: Spin rate, heading, and flip detection

**Files:**
- Create: `lib/melty/spin.h`, `lib/melty/spin.cpp`
- Test: `test/test_spin/test_spin.cpp`

**Interfaces:**
- Produces:
```cpp
constexpr float kClipG = 15.5f, kGravity = 9.80665f;
float rpmFromAccel(float radialG, float radiusM);
class HeadingTracker {
public:
  void update(float radialG, float radiusM, float trimRadPerSec, uint32_t dtUs, uint32_t nowMs);
  float headingRad() const;   // wrapped to [0, 2pi)
  float rpm() const;
  bool sensorOk(uint32_t nowMs) const;   // false after 500 ms with no good reading
};
class FlipDetector {
public:
  void update(float zG, int zSign, uint32_t filterMs, uint32_t dtMs);
  bool flipped() const;
};
```

`rpmFromAccel` uses `omega = sqrt(a / r)`, converted to RPM. A reading is good when it is finite, positive, and below `kClipG`. Bad readings keep the last good RPM and keep advancing heading from it, and do not refresh the sensor timer. `FlipDetector` is a first-order low-pass on `zG * zSign`, flipped when the filtered value is below 0.

### Task 5: Motor output, ramp, jam guard, LED

**Files:**
- Create: `lib/melty/drive.h`, `lib/melty/drive.cpp`
- Test: `test/test_drive/test_drive.cpp`

**Interfaces:**
- Consumes: `Settings` is defined in Task 6, so this task takes plain values.
- Produces:
```cpp
struct MotorPulses { uint16_t aUs, bUs; };
constexpr MotorPulses kNeutral{1500, 1500};
float rampStep(float current, float target, float ratePerSec, uint32_t dtMs);   // up limited, down immediate
class JamGuard {
public:
  float apply(float power, float rpm, float capPower, float minRpm, uint32_t dtMs);
};
struct DriveInput { float spin, x, y, headingRad, rpm; bool translationAllowed; };
struct DriveTuning { float minRpm, strength, phaseRad; bool reverseA, reverseB; };
MotorPulses computePulses(const DriveInput& in, const DriveTuning& t);
bool ledOn(float headingRad, float arcRad, bool sensorOk);
float effectiveHeading(float headingRad, bool flipped);   // flipped ? -heading : heading, wrapped
float stick(uint16_t ch);                                 // 1000..2000 to -1..1, 5% deadband
float spinCommand(uint16_t ch3);                          // 1000..2000 to 0..1
```

Algorithm for `computePulses`, with `mag = min(1, hypot(x, y))` and `dir = atan2(x, y)`:

```text
s    = cos(heading - dir - phase) >= 0 ? 1 : -1
d    = (translationAllowed && rpm >= minRpm && mag > 0) ? strength * mag * s : 0
powerA = clamp(spin + d, 0, 1), powerB = clamp(spin - d, 0, 1)
pulse = 1500 + 500 * power, or 1500 - 500 * power if that motor is reversed
```

The wheels face opposite ways, so one motor gains while the other loses. That is why A and B have opposite signs on `d`.

### Task 7: ESP32 drivers and main loop

**Files:**
- Create: `src/esc.h`, `src/esc.cpp`, `src/mpu.h`, `src/mpu.cpp`, `src/store.h`, `src/store.cpp`
- Modify: `src/main.cpp`

**Interfaces:**
- Consumes: everything in `lib/melty`.
- Produces:
```cpp
void escBegin(uint32_t hz);                  // starts both channels at 1500 us before returning
void escWrite(MotorPulses p);
bool mpuBegin();                             // +/-16g, wake, 400 kHz, Wire timeout 2 ms
bool mpuRead(float& xG, float& yG, float& zG);
bool mpuRestCheck();                         // magnitude 0.7 to 1.3 g on 3 reads, not all zero
void storeLoad(Settings& s);                 // falls back to defaults if missing or !settingsValid
void storeSave(const Settings& s);           // Preferences, versioned blob
```

`setup()` order: `escBegin` first, then load settings, then `Serial`, `Serial2` on GPIO16, sensor, then a 250 ms task watchdog. `mpuRestCheck` feeds `Safety::setSensorStartupOk`. Do not check `WHO_AM_I` for one exact value, since the spec calls out clone chips.

`loop()` at about 1 kHz, driven by `micros()`:

```text
drain Serial2 into IbusParser, feed Safety; Safety.update(now)
mpuRead into HeadingTracker and FlipDetector; on a failed read pass NAN to HeadingTracker and skip FlipDetector
if !armed: spin state 0, escWrite(kNeutral), LED off, poll console, status at 5 Hz, reset watchdog, return
target = spinCommand(ch3); ramp; JamGuard
computePulses with effectiveHeading, translationAllowed = sensorOk
escWrite only on the output period; LED from ledOn; RunLog at 50 Hz; reset watchdog
```

Trim comes from `stick(ch[3]) * trimRadPerSec`. The radial value uses `radialAxis` and `radialSign`. On a disarmed-to-armed change, clear the log, reset ramp and jam state. If `outputHz` differs after a settings change, call `escBegin` while disarmed.
